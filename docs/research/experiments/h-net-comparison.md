# H-Net と2番目の組を同じ費用で比べる

2026-11-04 に、測る前に決めた。H-Net が同じ費用で BPE のモデルより良いかを比べる。外側の層を Mamba-2（論文の形）、Mamba-3、Gated DeltaNet にした3通りを測る。コードと設定は `h-net/` にある。

## 条件

- 比べる相手：research の今の学習データ（2026-11-04 から FineWeb、training-data.md）で学習し直した2番目の組（second-bundle.md の形）。H-Net の側では学習しない。
- データ：同じ train.bin の文書を、同じ順のままバイトに直して読む（bytes_from_tokens.py）。行は2番目の組と同じく文書の頭から始まり、同じ文書の集まりから選ばれる。1行は、BPE の1,024トークンが平均で持つバイト数で、FineWeb では3,840バイト（val.bin で1トークン平均3.81バイト）。英語だけなので、日本語での効果はこの比較では測れない。
- 機械：Vast.ai の H100 SXM 80GB を1枚。イメージは基準と同じ。
- 費用：基準（baseline.md）を同じ機械で短く動かし、954回の更新にかかる時間を出す。各モデルの更新の回数は、その時間で読める回数にする（speed.py と同じ計算）。H-Net は区切りを6バイトごとに固定して時間を測る。学習の始めは約2バイトごとに区切るため、短い計測では本番より遅く見える。本番の学習時間は記録し、決めた時間とずれたら書く。
- H-Net：本体は2番目の組と同じ10層・幅640で、まとまりの上で動く。value embeddings はトークンごとの表なので外した。外側は幅512で、エンコーダとデコーダが4層ずつ。区切りの目標は6バイト、比率の損失の重みは0.03（論文と同じ）。1回の更新で512行（32行を16回）。外側の層の学習率は未調整で、AdamW の他の重みと同じ0.0044。Mamba-2 は畳み込みを PyTorch で計算する経路で動かす。速い経路が使う causal-conv1d には、この PyTorch 向けのビルド済みのものがないため。この経路は途中の値を多く残すので、1回に読む行を減らした。
- 採点：2番目の組と同じものを同じ文章で測る。検証の BPB は scoring.py と同じ行（val.bin の最初の2²⁰トークン、1行1,024トークン）のバイトを読み、scoring.py が数えるバイト数で割る。harness.py の英語6課題と日本語3課題の、正解率と正解の BPB。日本語の課題も同じく測るが、読み方には使わない。

## 結果を見る前に決めた読み方

- 検証の BPB と、英語6課題の正解の BPB の平均を、2番目の組と比べる。検証の BPB で0.3%（scoring.md）、正解の BPB の平均で1.3%（second-bundle.md）を、種による揺れとする。それを超えて低ければ H-Net の勝ち、超えて高ければ負け、その間は差が測れないと読む。
- 測る前の予想は、3通りとも負け。外側の層は、Gated DeltaNet と Mamba-3 が Mamba-2 より良い。

## 結果：Mamba-2（2026-11-04）

Vast.ai の H100 SXM 80GB（日本、$2.41/時）で1回。決めた読み方で、H-Net（Mamba-2）の負け。検証の BPB は2.431で、2番目の組の FineWeb での1.2146（third-bundle.md、scoring.py と同じ行）の2.0倍だった。揺れとした0.3%をはるかに超える。正解の BPB は測っていない。検証の BPB が2倍違うので、測っても負けの読みは変わらないと判断した（未確認）。

| 項目 | 値 |
|---|---|
| 基準の1回の更新、起動 | 0.830秒、37秒 |
| H-Net の1回の更新、起動（区切りを6バイトに固定して計測） | 3.93秒、129秒 |
| 同じ費用で回せた更新 | 178回（基準は954回。2番目の組は FineWeb で1,275回、third-bundle.md の別の借り） |
| 学習の時間（起動から保存まで） | 約13分。決めた費用は829秒で、ほぼその通り |
| 区切りの長さ | 目標の6バイトに届かず、最後は約2.7バイト。途中で一時63バイトまで振れた |
| 学習の最後の損失（バイトあたり nats、比率の損失を含む） | 学習 1.7273、検証 1.7245 |
| 検証の BPB（scoring.py と同じ行、401万バイト） | 2.431 |
| 正解の BPB と正解率（harness.py） | 未測定。この機械に lm-eval を入れていない |

- 1回の更新で読むのは、H-Net が約197万バイト（512行×3,840バイト）、2番目の組が約200万バイト（524,288トークン×3.81バイト）でほぼ同じ。同じ費用で読んだ量は、H-Net が2番目の組の約7分の1だった。
- この測定は、research の枠が CORE と30分の学習に変わる前の決め方（基準の費用、BPB）で測った。新しい枠では測っていない。
- H-Net は1回の更新が基準の4.7倍遅く、同じ費用では基準の5分の1以下しか更新できなかった。遅さの内訳は測っていない。Mamba-2 を融合しない経路で動かしたこと、1回に32行しか読まず16回回すこと、本体を層ごとに Python から呼ぶことが効いていると推測する。
- 区切りが目標より細かく、本体が読むまとまりは計測時の約2.2倍になった。そのため学習中の1回の更新は約4.4秒で、計測の3.93秒より遅かった。
- 機械は借りてから消すまで約31分、約 $1.25。導入の失敗2回（mamba-ssm の setup.py が nvcc なしで止まった、pyarrow がなかった）で約10分を失った。
- 検証の BPB は score_hnet.py の validation_bits で測った（`--validation-only` と同じ計算）。重みは out/h-net-rental/models/hnet-mamba2 にある。


## 速さの内訳と直したこと（2026-11-05）

上の測定で1回の更新が基準の4.7倍だったので、遅い原因を調べて直し、Vast.ai の H100 SXM 80GB（日本、$2.14/時）を1台借りて、同じ機械で直す前と後を測った。データは乱数のバイトで、区切りは6バイトごとに固定し、1回の更新は512行。直す前のコードはこの前のコミット（2132b32）のものを同じ機械に送って測った。借りていたのは約30分、約 $1.1。

| 形 | 1回の更新 | メモリの最大 |
|---|---|---|
| 直す前（Mamba-2 は融合しない経路、32行×16回） | 3.917秒 | 25.7 GB |
| GPU の待ちとコンパイルだけ直す（同じ経路と回数） | 3.647秒 | 24.6 GB |
| さらに Mamba-2 を融合した経路に（32行×16回） | 2.651秒 | 19.5 GB |
| 同（64行×8回） | 2.616秒 | 38.0 GB |
| 同（128行×4回） | 2.583秒 | 75.0 GB |
| 同、区切りを2バイトごとに（64行×8回） | 3.412秒 | 58.0 GB |
| 2番目の束（乱数のトークン、128本×4回） | 0.616秒 | 45.7 GB |

- 融合した経路：mamba-ssm の融合した経路は畳み込みを causal-conv1d の CUDA 関数で計算するが、この PyTorch 向けのビルドがない。同じ引数で動く畳み込みを Triton で書いて差し込んだ（h-net/causal_conv.py）。CPU 上の Triton のインタープリタで PyTorch の畳み込みと勾配まで一致し、H100 でも融合しない経路との差は最大で2.0%（dt_bias の勾配、bf16 の丸め）だった。更新は27%速くなった。
- GPU の待ち：32行ごとに3回 GPU を待っていた（まとまりの位置、最長の行の長さ、区切りの割合）。後の2つをなくし、待つのはまとまりの数を知る1回だけにした。プロファイルで GPU が動いている時間の割合は92.3%（直す前、32行）から97.1%（直した後、128行）になった。まとまりの数に上限を決めて大きさを揃える案は採らなかった。上限を超える行の区切りを削ると、どのバイトが区切りになるかが後ろのバイトに左右され（因果が崩れる）、上限まで埋める空きの計算も無駄になるため。
- コンパイル：本体を層ごとに20個のグラフに分けていたのを1つにし、外側の層の前後の正規化と足し算、区切りの確率、予測と損失もコンパイルした。待ちの変更と合わせて7%速くなった。最初の更新（起動）は、冷えた状態どうしで84秒と85秒で変わらなかった。新しい枠では起動は30分に数えない。
- 1回に読む行数：128行でも32行より2.6%しか速くなかった。FineWeb で64行×8回の学習を試すと、区切りがまだ細かい9回目の更新でメモリが尽きた（確保67.5 GB、空きのまま予約9.9 GB）。32行のままにした。
- 区切りが細かいほど遅い：2バイトごとでは6バイトごとより30%遅かった（64行）。11-04 の学習は最後に約2.7バイトだった。

直した後のプロファイル（128行、2回の更新）では、GPU の時間のうち causal_conv.py の畳み込みの逆向きが28.5%、Mamba-2 の SSD が29.0%、行列積が15.4%、コンパイルした部分が9.2%、Mamba-2 の正規化が6.9%、注意が2.3%だった。直す前は、融合しない経路の値の写しが28.8%、cuDNN の depthwise の畳み込みが15.9%を占めていた。

- 畳み込みの逆向きは1回22.8ミリ秒で、読み書きの量から見積もる約1.5ミリ秒より遅かった。sm_90 向けの ptxas で、64位置×128チャンネルのタイルが1スレッドあたり約24 KB をメモリにあふれさせていた。タイルを16〜64位置にし、GPU 上で5通りから選ぶようにして、あふれは0〜52バイトになった（98b78c1）。速さはまだ測っていない。帯域どおりになれば、1回の更新は約1.9〜2.0秒、2番目の束の約3倍と見積もる。
- その場合も時間の多くは外側の Mamba-2 にかかるので、外側の幅を512から256にした。幅256では、外側の層の行列積は約4分の1、SSD と畳み込みと正規化は約半分になる。
- 区切りが目標より細かいあいだは、比率の損失の重みを上げるようにした（512行ごとに、目標の比率×区切りの割合−1 の0.1倍だけ対数で動かし、0.03を下限、1を上限にする）。論文は0.03のまま。区切りが細かくなり始めたのは11-04 の学習で更新68回目からで、学習の最初はむしろ粗く（更新25回目に63バイト）、最初だけ区切りを固定しても届かないため。
- CPU で小さな H-Net（外側は畳み込みで幅64、本体は2層で幅128、1回の更新は512バイトを16行）を FineWeb の学習データの文章で400回学習させた（重みの動きは1回の更新あたり本番と同じにした）。重みを0.03に固定すると区切りは更新60回目の4.5バイトから400回目の3.25バイトまで細かくなった。動かす速さが0.03では4.7〜5.3バイトで止まり重みは上がり続け、0.1では更新80回目から5.4〜6.2バイトに保たれ、重みは360回目に上限の1に達した。揺れはなかった。交差エントロピーは、粗い区切りのぶん400回目で約3%高かった。本番の大きさでの動きはまだ見ていない。
- 学習の記録の損失には、重み×比率の損失（目標の比率で1）が入る。重みが動くと比べられなくなるので、交差エントロピーを別に出すようにした。
