# 2番目の束のコードの確認

2026-11-01 に、RoPE、RMSNorm、QK-norm、ReLU²、出力のゼロ初期化を足したコードが動くことを、GPU なしの処理用の機械（CPU）で確かめた。**効果は測っていない。** 項目を足すたびに同じ確認をした。下の数字は5項目がそろったときのもの。

## 小さいモデルの確認

2層、幅64、ヘッド2、文脈64、1回8本×2回、float32、compile なし。

| 確認 | 結果 |
|---|---|
| テスト | 全111件が通過 |
| 基準、Muon、最初の束（6回の更新） | 変更の前後で損失が完全に一致 |
| 2番目の束から足した項目を外す（6回の更新） | 変更の前後で損失が完全に一致 |
| 2番目の束（全部入り、20回の更新） | 検証の損失が9.02から7.56 |
| 途中からの再開、採点 | 動作。検証の BPB は2.72 |
| 基準と最初の束の保存済みの重み | 読めて、足した項目はオフになる |

## 実サイズの出だし

10層、幅640の2番目の束（RoPE、RMSNorm、QK-norm、ReLU²、Value embeddings、共有の埋め込み）で、出力の重みの初期値を今の小さい値と0にして、同じ種で比べた。1回の更新は4本×文脈256（本来の約500分の1）、float32、compile なし。Muon の直交化だけ float32 に変えた。

| 更新 | 小さい値 | 0 |
|---|---|---|
| 学習前の検証の損失 | 9.14 | 12.82 |
| 1回目の学習の損失 | 9.14 | 12.80 |
| 2回目 | 8.42 | 8.16 |
| 3回目 | 7.93 | 7.94 |
| 6〜10回目の平均 | 8.13 | 8.11 |
| 11〜20回目の平均 | 7.71 | 7.72 |
| 21〜30回目の平均 | 7.50 | 7.55 |

バッチが小さく回数も少ないので、出だしの確認にしかならない。

## 埋め込みの分離を足したとき

同じ日に、入力と出力の埋め込みの分離を足して、同じ確認をした。テストは全126件が通過。外したときの損失は前のコードと完全に一致。全部入りの小さいモデル（20回の更新）は検証の損失が9.01から7.41で、途中からの再開と採点も動く。実サイズのパラメータは、計算に使うものが5,440万で変わらず、全体は8,061万から8,585万。

実サイズの出だし（条件は上と同じで、出力の重みは0から）：

| 更新 | 共有、学習率0.004 | 分離、入力0.66、出力0.0044 |
|---|---|---|
| 学習前の検証の損失 | 12.80 | 9.01 |
| 1回目の学習の損失 | 12.79 | 9.01 |
| 2回目 | 8.21 | 8.91 |
| 3回目 | 8.14 | 8.43 |
| 6〜10回目の平均 | 8.06 | 7.58 |
| 11〜20回目の平均 | 7.73 | 7.35 |
| 21〜30回目の平均 | 7.48 | 7.33 |
| 31〜34回目の平均 | 7.41 | 7.10 |

入力の学習率0.66でも、この範囲で学習は発散しなかった。バッチが小さく回数も少ないので、品質の比較ではない。

## 確かめていないこと

- GPU で動くか。速さも測っていない。QK-norm の費用は分からない。
- 実サイズで最後まで安定して学習するか。

## 確かめ方で分かったこと

- 損失を前後で比べるときは1スレッドにする（`OMP_NUM_THREADS=1`）。2スレッドだと、同じコードでも小数第4位で変わる。
- 実サイズの Muon は、この CPU では bf16 の行列の積が遅く、最初の更新が280秒で終わらなかった。float32 に変えると1回約7秒（4スレッド）。
- ファイルに書くログは溜まるので、途中で止める学習は `PYTHONUNBUFFERED=1` にする。止めると溜まった分が消える。
- CPU で採点するときは `--device cpu --precision float32 --batch-tokens 4096` を付ける。
