# 表を引く方法（Engram、COUNT、STEM、L³）

トークンや直前の数トークンから表を引いて、モデルの計算に足すか置き換える方法。表を引く計算はほとんどなく、増えるのは主にメモリ。COUNT は2026-11-03 に3番目の束へ入れた（下の「3番目の束での形」）。今の規模では測っていない。

## トークンだけで引く表

- [STEM](../sources/stem.md) は MLP の入口を表に置き換え、3.5億の点の平均が 49.72 から 50.90 になり、FLOPs も少し減る。ゲート付きの MLP が前提で、今の ReLU² の形にはそのまま入らない。
- [L³](../sources/l3.md) は層の間に表を足し、同じ FLOPs の8億級で 48.28 から、1層で 49.10、2層で 49.45、表を広くした3層で 50.25 になる。速さは約87%。表は1層あたり71万個の埋め込みで、今の幅640と値の幅512で数えると1層で約8億パラメータ（今のモデル全体の約10倍）。
- STEM の読む量は今より桁違いに多い。L³ の8億級は1パラメータ約12トークンで、今と同じくらい。今の Value embeddings（1層おき）も同じ種類の表で、語彙8,192では表は小さい。

## 学習しない表（COUNT）

[COUNT](../sources/count-ngram.md) は、コーパスの n-gram を数えた表をメインのメモリに置き、続きやすいトークンの出力の表を頻度で重み付けして入力に足す。学習するパラメータは増えない。

- 60M〜1B、1パラメータ10〜40トークンで、検証の損失は計算 46〜89% 増し、課題の損失は 6〜56% 増しに相当し、41の選択式の課題の点もほとんどの予算で上がる（[`language-model` のメモ](https://github.com/tomato414941/language-model/blob/main/docs/research/sources/count-ngram.md)）。計算量2倍で約3.9%という換算なら、検証の損失で約2〜3.6%、課題の損失で約0.3〜2.5%。
- 今の束は5,400万、1パラメータ12トークンで、計算量は約2×10¹⁷。論文の一番小さい点（6,000万、D/N=10）と同じくらいで、差はここが一番大きい。図の読み取りで、41課題の正解率が 29.7→31.3、正解の BPB が 2.05→1.91。
- 1つの研究だけで、基準は AdamW。今の束は Muon などで既に伸びているので、重なる分は小さくなるかもしれない。表は Dolma 3 全体（約6兆トークン）から作っていて、少ないデータで数えた表でも同じだけ効くかは試されていない。

## 学習する表

- **speedrun：** [記録 #92](../sources/modded-nanogpt-anvil2.md) は、行数を377,280から8,460万にすると検証損失が約3.315から3.279になる（約1.1%）。時間はほぼ同じで、4分の1の行でも大半が残る。
- **自動の探索：** [Recursive](../sources/recursive-first-steps.md) の一番良い解は、2トークンと3トークンの表に約28億パラメータを使う。表だけの効果は分けられていない。
- **メモリを減らす：** [Low-Bit N-Gram](https://github.com/tomato414941/language-model/blob/main/docs/research/sources/low-bit-ngram.md) は、4ビットにしてメモリが約75%減り、効果の99%以上が残るとする。
- **小さい規模の古い結果：** nanochat の LOG（2026-01-27、28）では、完全な形の改善はわずかで、ゲートも3トークンも効かず、前半の層だけに入れると悪化した。一番良かったのは2トークンの表を全層に足す形で、12層では勝ったが、25層では時間で比べると効果が消えて取り除かれた。Marin では約0.2%（[bigram hash のメモ](https://github.com/tomato414941/language-model/blob/main/docs/research/topics/bigram-hash-embedding.md)）。記録 #92 より表がずっと小さい。
- **COUNT との比較：** COUNT の著者は、GPU のメモリが限られるなら、学習する表より本体にメモリを使うほうが良いとしている。

## 大規模

- [Engram の論文](../sources/engram.md)では、同じ計算量で MoE より検証 loss が0.7%と1.5%低い。計算量を約1.14倍と約1.3倍にしたのと同じくらい（自分たちの換算）。最小の実験でも基準の約730倍の計算量で、loss の実験はすべて MoE の上。
- [Tokenizer-Agnostic Engram](../sources/tokenizer-agnostic-engram.md) では、ベンチマークの平均は上がったが、wikitext の BPB は0.861から0.919へ悪化した（各1回）。物差しが BPB なので注意が要る。
- 12層の最後の層に入れても効果の64%が残るので、「前半の層を楽にする」だけでは説明しきれないと見ている。表を切った実験でも MATH が36%まで落ちるので、「知識は表にある」も弱い根拠。
- DeepSeek-V4（arXiv 2606.19348）は使わず、今後探る方向に挙げた。DeepSeek-V4.1-Flash は1,960億パラメータを Engram に割いている（Low-Bit N-Gram の要旨から。元の報告は読んでいない）。[Marin の記事](../sources/marin-moe.md)は見送っている。

RETRO（retrieval.md）と違って、文章そのものを持たず、短い語句しか引けない。DB も検索も要らず、長い文章の丸写しもできない。

## 今の条件に当てはめると

自分たちの計算と読みで、測っていない。

- **行の数：** 語彙8,192なので2トークンの組は最大約6,700万で、語彙50,304の25億より少ない。少ない行で足りる可能性がある。
- **表の大きさ（[数えた](../experiments/count-table-check.md)）：** ClimbMix の20億トークンから、上位8候補で下限4回なら約5.4GB、下限8回なら約2.3GB。論文の17GB より小さい。FineWeb の20億トークンで作った3番目の束の表は5.3GB。
- **メモリ：** 学習する表は GPU に置く。今の束は H100 の80GB のうち約51GB を使っている。COUNT の表はメインのメモリに置けるが、この大きさなら GPU の空きにも入る。
- **入力の大きさ：** 2番目の束の重みでは、入力の表の値が約17.9、出力の表の値が約0.12（行ごとの RMS の平均）で、約150倍違う。論文のように足してから正規化すると COUNT の分が消えるので、別々に揃えてから足す必要がある。
- **重複の影響：** [speedrun の PR #367](../sources/modded-nanogpt-retrieval.md) は、学習データからの完全一致の検索をヒントにして、同じ機械で40.5秒を6.7秒にした。メンテナはこれを、検証の損失と汎化の差を示すものと見ている。表による検証の損失の改善には、学習と検証で重なる文章の分が入っている可能性があるので、点でも確かめる。
- **表の文章と学習の文章：** 2026-11-03 時点の見方では、学習が読まない部分で表を作る。
  - 学習データの20億トークンで下限4回の表を作ると、行が見つかったときに次のトークンが上位8に入る割合は、履歴5で、数えた文章83%、検証の文章57%（[数えた](../experiments/count-table-check.md)）。モデルが学習中に表を信じすぎる可能性がある。点への影響は測っていない。
  - 論文は同じコーパスで数えるが、表の元の文章は読む量の150〜1万倍で、行は数百回以上現れた履歴なので、この差は小さいはず。今は文章が読む量の約3倍で、下限も低い。
  - 別の分野にも同じ問題がある。[CatBoost](../sources/catboost.md) はこれを target leakage と呼び、自分だけ抜いても防げないとする。データを分ける方法の短所はデータが減ることだが、ClimbMix は約99.5%を読んでいないので、その短所は小さい。[RETRO](../sources/retro.md) は同じ文書の近傍を除き、[speedrun の PR](../sources/modded-nanogpt-retrieval.md) は、前のステップだけから引くか、読まないシャードで数える。
  - 同じ文章で作る形と並べて測ったら見直す。
- **何から作るか：** 2026-11-03 時点の見方では、[FineWeb](../sources/fineweb.md) の 10BT の標本。
  - **ClimbMix を使わない理由：** 混ぜ方が、6課題のうち3課題（PIQA、ARC-Easy、HellaSwag）の検証用の問題での成績で選ばれている。表はその文章の続きをそのまま渡せる。ライセンスも非商用。
  - **FineWeb にした理由：** 1つの手順で作った一般の Web の文章で、混ぜ方の最適化をしていない。ODC-By。手順を選ぶ実験には HellaSwag、PIQA、ARC、MMLU を含む8課題の成績を使っていて、まったく中立ではない。
  - **選ばなかったもの：** FineWeb-Edu、Nemotron-CC、Cosmopedia は ClimbMix の元。DCLM の品質の分類器は課題の成績で選ばれていて、Nemotron-CC の品質の判定にも使われている。[Common Pile](../sources/common-pile.md) は論文、コード、特許が多く、重みも小さいモデルの成績で決めていて、HellaSwag と PIQA で弱い。論文が使った Dolma 3 は CC が76%で、混ぜ方を小さいモデルで課題の成績から最適化したという二次的な説明があるが、一次資料では確かめていない。分野を絞ったデータは、6課題に近い分野を選ぶと評価に合わせることになるので使わない。[MassiveDS](../sources/massiveds.md) でも、分野を混ぜたデータストアが分野ごとのものと同等以上。
  - **代わりに失うもの：** 同じ大きさの表で、モデルが読む ClimbMix の文章に当たる割合が、直前3〜5トークンで2〜4割低い。20億トークンの表でも同じくらいだった。どちらでもない v6 の英語でも、ClimbMix の表のほうが当たる（[測った](../experiments/count-table-check.md)）。論文や [kNN-LM](../sources/knn-lm.md) のように、学習と同じ種類の文章を多く数える形からは離れる。点への影響は測っていない。
  - **得るもの：** 表が学習データとも検証とも別のデータになり、学習中と本番の当たり方が揃う。[Infini-gram](../sources/infini-gram.md) では、参照と同じデータで学習したモデルほど改善が小さい。学習データを変えても、表は作り直さなくてよい。
  - ClimbMix の表と並べて測ったら見直す。
- **数える量：** 同じ大きさの表なら、文章を2倍にするごとに当たり方が1〜3ポイント上がる（20億までの実測）。kNN-LM、MassiveDS、RETRO の DB でも、大きくするほど良くなり続ける。学習の費用は変わらないので、処理用の機械で数えられる範囲で増やせる。2026-11-03 時点では、まず学習データと同じ20億トークンにする。今の作り方ではディスクが40億トークンほどで足りなくなり、それより先は作り方を変える必要がある。COUNT が今の規模で効くと分かってから増やす。
- **評価の問題の漏れ：** 5トークンの履歴から続きを直接引けるので、評価の問題が入っていると、重みの中に残る場合より点に出やすいかもしれない。正解率を見るので、評価の問題を含む文書（学習データでは0.114%）は数えない形にする。表を作る文章でも同じように探す。
- **費用：** 学習の時間で揃える今の比較には、表の作成と転送は入らない。費用としては別に書く。5.3GB の転送は前回の速さで約4分、約 $0.16。転送は学習のたびにかかる。表は処理用の機械で作れて、FineWeb の20億トークンで、文章の準備に約34分、数えるのに約1.6時間かかった（[内訳](../experiments/count-table-check.md)）。一度作れば、どの学習でも使い回せる。

## 3番目の束での形

設定は `configs/bundle3.py`、表を作るのは `count_data.py` と `count_table.py`。

- **入れた経緯：** 保存したモデルの出力に表を混ぜる無料の確認を提案したが、確認をせずに入れた（2026-11-03）。効果は束の測定でまとめて見る。
- **表：** FineWeb の 10BT の標本（リビジョン `9bb295d`）の先頭から、評価の問題を含む文書を除いた20億トークン。直前0〜5トークンの履歴で、4回以上現れたものに、続く上位8トークン。点数は `C(h,w)/C(h)` を1バイトに丸めたもの。短い履歴から候補を埋める処理はしない。履歴は BOS で始まってもよいが、途中に BOS を含まない。5.3GB。ClimbMix の検証の文章で、次のトークンが候補に入る位置は履歴3で38%、履歴5で9%（[測った](../experiments/count-table-check.md)）。
- **段落の区切り：** FineWeb は段落を改行1つで区切り、改行2つを含むトークンがない。ClimbMix の検証の文章ではトークンの0.95%がそれで、それを含む履歴（履歴5で4.7%の位置）は表で見つからない。FineWeb では段落と行の区切りを見分けられないので、合わせずに使う。
- **引き方：** 学習中に GPU の上で、長さごとにキーを二分探索する。6つの長さの候補の行を点数で重み付けして足し、6で割る。見つからない長さも数に入れるのは論文と同じ。足すのは出力の表の行で、勾配は出力の表に流れる。
- **入力への足し方：** 出力の表の行は入力の表の約150分の1の大きさなので、別々に大きさを揃えてから、学習する重み（初期値0.1、x0 の重みと同じ学習率）を掛けて足す。論文は足してから LayerNorm をかける。
- 論文と違う点（表の元、量、段落の区切り、足し方、オプティマイザ）が多いので、効かなかった場合はまずここを見直す。

## 見方が変わりそうな条件

- 今の規模で測って、効果が見込みより小さかった場合。特に正解率が動かなかった場合。
- MoE を入れる場合。Engram の論文の結果は MoE の上のもの。
- 推論の費用も数える課題に変える場合。表のメモリが費用になる。
