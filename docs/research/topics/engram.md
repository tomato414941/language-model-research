# 表を引く方法（Engram、COUNT、STEM、L³）

トークンや直前の数トークンから表を引いて、モデルの計算に足すか置き換える方法。表を引く計算はほとんどなく、増えるのは主にメモリ。2026-11-02 時点の見方では、次の束で最初に検討する候補。今の規模では測っていない。

## トークンだけで引く表

- [STEM](../sources/stem.md) は MLP の入口を表に置き換え、3.5億の点の平均が 49.72 から 50.90 になり、FLOPs も少し減る。ゲート付きの MLP が前提で、今の ReLU² の形にはそのまま入らない。
- [L³](../sources/l3.md) は層の中に表を置き、同じ FLOPs の8億で 48.28 から 50.25 になる。速さは約87%。
- STEM の読む量は今より桁違いに多い。L³ の読む量は読んだ範囲で確かめていない。今の Value embeddings（1層おき）も同じ種類の表で、語彙8,192では表は小さい。

## 学習しない表（COUNT）

[COUNT](../sources/count-ngram.md) は、コーパスの n-gram を数えた表をメインのメモリに置き、続きやすいトークンの出力の表を頻度で重み付けして入力に足す。学習するパラメータは増えない。

- 60M〜1B、1パラメータ10〜40トークンで、検証の損失は計算 46〜89% 増し、課題の損失は 6〜56% 増しに相当し、41の選択式の課題の点もほとんどの予算で上がる（[`language-model` のメモ](https://github.com/tomato414941/language-model/blob/main/docs/research/sources/count-ngram.md)）。計算量2倍で約3.9%という換算なら、検証の損失で約2〜3.6%、課題の損失で約0.3〜2.5%。
- 今の束は5,400万、1パラメータ12トークンで、計算量は約2×10¹⁷。論文の一番小さい点（6,000万、D/N=10）と同じくらいで、差はここが一番大きい。図の読み取りで、41課題の正解率が 29.7→31.3、正解の BPB が 2.05→1.91。
- 1つの研究だけで、基準は AdamW。今の束は Muon などで既に伸びているので、重なる分は小さくなるかもしれない。表は Dolma 3 全体（約6兆トークン）から作っていて、少ないデータで数えた表でも同じだけ効くかは試されていない。

## 学習する表

- **speedrun：** [記録 #92](../sources/modded-nanogpt-anvil2.md) は、行数を377,280から8,460万にすると検証損失が約3.315から3.279になる（約1.1%）。時間はほぼ同じで、4分の1の行でも大半が残る。
- **自動の探索：** [Recursive](../sources/recursive-first-steps.md) の一番良い解は、2トークンと3トークンの表に約28億パラメータを使う。表だけの効果は分けられていない。
- **メモリを減らす：** [Low-Bit N-Gram](https://github.com/tomato414941/language-model/blob/main/docs/research/sources/low-bit-ngram.md) は、4ビットにしてメモリが約75%減り、効果の99%以上が残るとする。
- **小さい規模の古い結果：** nanochat の LOG（2026-01-27、28）では、完全な形の改善はわずかで、ゲートも3トークンも効かず、前半の層だけに入れると悪化した。一番良かったのは2トークンの表を全層に足す形で、12層では勝ったが、25層では時間で比べると効果が消えて取り除かれた。Marin では約0.2%（[bigram hash のメモ](https://github.com/tomato414941/language-model/blob/main/docs/research/topics/bigram-hash-embedding.md)）。記録 #92 より表がずっと小さい。
- **COUNT との比較：** COUNT の著者は、GPU のメモリが限られるなら、学習する表より本体にメモリを使うほうが良いとしている。

## 大規模

- [Engram の論文](../sources/engram.md)では、同じ計算量で MoE より検証 loss が0.7%と1.5%低い。計算量を約1.14倍と約1.3倍にしたのと同じくらい（自分たちの換算）。最小の実験でも基準の約730倍の計算量で、loss の実験はすべて MoE の上。
- [Tokenizer-Agnostic Engram](../sources/tokenizer-agnostic-engram.md) では、ベンチマークの平均は上がったが、wikitext の BPB は0.861から0.919へ悪化した（各1回）。物差しが BPB なので注意が要る。
- 12層の最後の層に入れても効果の64%が残るので、「前半の層を楽にする」だけでは説明しきれないと見ている。表を切った実験でも MATH が36%まで落ちるので、「知識は表にある」も弱い根拠。
- DeepSeek-V4（arXiv 2606.19348）は使わず、今後探る方向に挙げた。DeepSeek-V4.1-Flash は1,960億パラメータを Engram に割いている（Low-Bit N-Gram の要旨から。元の報告は読んでいない）。[Marin の記事](../sources/marin-moe.md)は見送っている。

RETRO（retrieval.md）と違って、文章そのものを持たず、短い語句しか引けない。DB も検索も要らず、長い文章の丸写しもできない。

## 今の条件に当てはめると

自分たちの計算と読みで、測っていない。

- **行の数：** 語彙8,192なので2トークンの組は最大約6,700万で、語彙50,304の25億より少ない。少ない行で足りる可能性がある。
- **表の大きさ（[数えた](../experiments/count-table-check.md)）：** ClimbMix の20億トークンから、上位8候補で下限4回なら約5.4GB、下限8回なら約2.3GB。論文の17GB より小さい。
- **メモリ：** 学習する表は GPU に置く。今の束は H100 の80GB のうち約51GB を使っている。COUNT の表はメインのメモリに置けるが、この大きさなら GPU の空きにも入る。
- **入力の大きさ：** 2番目の束の重みでは、入力の表の値が約17.9、出力の表の値が約0.12（行ごとの RMS の平均）で、約150倍違う。論文のように足してから正規化すると COUNT の分が消えるので、別々に揃えてから足す必要がある。
- **重複の影響：** speedrun の PR #367 は、学習データからの完全一致の検索をヒントにして、同じ機械で40.5秒を6.7秒にした。メンテナはこれを、検証の損失と汎化の差を示すものと見ている。表による検証の損失の改善には、学習と検証で重なる文章の分が入っている可能性があるので、点でも確かめる。
- **評価の問題の漏れ：** 5トークンの履歴から続きを直接引けるので、評価の問題が入っていると、重みの中に残る場合より点に出やすいかもしれない。正解率を見るので、評価の問題を含む文書（0.114%）は数えない形にする。
- **費用：** 学習の時間で揃える今の比較には、表の作成と転送は入らない。費用としては別に書く。5.4GB の転送は前回の速さで約4分、約 $0.16。表は処理用の機械で作れる。

## 見方が変わりそうな条件

- 今の規模で測って、効果が見込みより小さかった場合。特に正解率が動かなかった場合。
- MoE を入れる場合。Engram の論文の結果は MoE の上のもの。
- 推論の費用も数える課題に変える場合。表のメモリが費用になる。
