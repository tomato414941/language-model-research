# H-Net（バイトを読み、まとまりを学習で決める）

トークナイザを使わず、UTF-8 のバイトを読む。どこでまとめるかをモデルと一緒に学習し、本体はまとまりの上で動く。論文と Cartesia の記事の数字は `language-model` の [h-net.md](https://github.com/tomato414941/language-model/blob/main/docs/research/topics/h-net.md) に、論文の仕組みと設定は[出典のメモ](../sources/h-net.md)にある。以下は2026-11時点の見方。

## 試す理由

日本語での公開の数字がない。日本語は1文字が3バイトで、語彙の小さい BPE はうまくまとめられない。論文では中国語の差が英語より大きかった。

ただし research の学習データは英語の FineWeb（2026-11-04 から）と、2026-11-05 からは FineMath と Common Pile のコードなので（[学習データ](training-data.md)）、research での比較で測れるのは英語だけ。日本語での効果は、日本語を含むデータで別に測る必要がある。

## 外側の層

論文はエンコーダとデコーダを Mamba-2 にし、すべて Transformer にした形が一番悪かった。Mamba-3 と Gated DeltaNet でも試す。どちらも選んで忘れる再帰を残したまま、Gated DeltaNet は状態の書き換え（デルタ則）で記憶を正確にし、Mamba-3 は状態に回転を入れて数え方を直したとされる。バイトから語をまとめ、語から1バイトずつ綴る外側の仕事に効くと推測している。H-Net の外側で比べた例は見つけていない。2つの論文の本文はまだ読んでいない。

## 同じ費用で比べたときの見込み

研究側の規模（本体5,440万パラメータ、学習は30分）では負けると見ている。

2026-11-04 の測定では、ここでの実装の H-Net（Mamba-2）は1回の更新が基準の4.7倍遅く、同じ費用で178回しか更新できなかった。検証の BPB は2.431で、同じデータの2番目の組（1.2146）の2倍だった。決めておいた読み方で負け（[同じ費用での比較](../experiments/h-net-comparison.md)）。速い実装なしには、この規模の比較は速さの差でほぼ決まる。

2026-11-05 に実装を直し、H100 で1回の更新は3.917秒から2.583〜2.651秒になった（同じ機械、区切りは6バイトごと）。Mamba-2 を融合した経路で動かし（畳み込みは Triton）、GPU を待つのを32行あたり1回にし、本体を1つのグラフにコンパイルした。それでも2番目の束（0.616秒）の約4倍で、時間の多くは外側の Mamba-2 にかかっていた（[速さの内訳](../experiments/h-net-comparison.md)）。そこで外側の幅を512から256にし、区切りが目標の6バイトより細かいあいだは比率の損失の重みを上げるようにした。畳み込みの逆向きの遅さも直した。同じ日に枠のとおり30分学習して1回測ると、1回の更新は1.55秒で、区切りは約5.5バイトに保たれた。それでも OLMES の3つの BPB と検証の BPB のすべてで、今の最良（research-v4）に負けた。QA は27%、検証の BPB は20%高い。Math と Code は2.5〜3倍だが、research-v4 は FineMath とコードも読み、H-Net は FineWeb だけを読んだので、差の多くは学習データによると見ている（[枠のとおりの1回](../experiments/h-net-comparison.md)）。読む量あたりでは、H-Net は research-v4 の約1.5倍遅い。Mamba-3 と Gated DeltaNet の外側は測っていない。

- 論文の勝ちは計算量をそろえた比較で、時間はそろえていない。著者の実装でも学習は最大2倍遅い。
- BPE を追い越すのは、論文の XL で1段が約1000億バイト、2段が約300億バイトを読んでから。それまではどの H-Net も BPE より悪い。ここでの学習は20〜30億バイトしか読まない。
- 2026-11-05 の1回は、2番目の束と比べて、読んだ量（22億と25億バイト）も1バイトあたりの計算量（概算）もほぼ同じで、検証の BPB が12%高かった。追い越す前は負けるという論文の見方と合う。
- 本体が小さいので、外側の層の計算の割合が大きい。幅を256にすると、外側の幅と本体の幅（640）の比は論文の1段の L（1,024と1,536）より小さくなる。

ここで負けても、本番の規模で効かないとは言えない。v6 の学習は約300億バイトを読んでおり、論文で追い越しが起きるあたりにある。

## 今の扱い：保留

採用はしないが、打ち切らない。負けたのは、ここの H-Net がまだ追い付いていないためと見ている。追い付いていないのは次の3つ。

- 論文のあとの改良。Cartesia の記事（[From Tokens to Bytes](https://cartesia.ai/blog/from-tokens-to-bytes-part-1)、2026-10-28）は、改良した H-Net（未公開）で BPE の Transformer のトークナイザの部分だけを置き換えて比べ、どの大きさでも損失が低かったとしている。表で一番小さい段は8層・幅640・本体5,640万パラメータで、ここの本体とほぼ同じ大きさ。比べたのは計算量とデータの量で、時間は書かれていない。改良の中身も書かれていないが、論文の H-Net は次のまとまりの最初のバイトを見てから区切る作りで、それが次のバイトの予測と段の重ね方を弱めたとしている。論文の H-Net のままでは、上の追い越しの位置から、この枠で勝つ見込みは薄い。
- 速さ。読む量あたり research-v4 の約1.5倍遅い（2026-11-05）。枠は時間でそろえるので、遅い分だけ読む量が減る。
- 比べ方。記事は区切りを強い補助損失で BPE のトークンと同じ大きさ（4.57バイト）にそろえ、外側の層を埋め込みと出力層に計算量とパラメータでそろえている。2026-11-05 の1回は区切りが5.5バイトで、FineWeb のトークン（3.81バイト）の1.4倍粗かった。学習データも本線と違い（FineMath とコードなし）、本体に本線の変更も入っていない。

改良版のコードか改良の中身が公開されたら、区切りの大きさと学習データと本体を本線にそろえて測り直す。
